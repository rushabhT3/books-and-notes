Q1What are the key advanced JavaScript concepts a senior React developer must master?▾

Closures — every React hook relies on closures. A stale closure is when a callback captures an old value of state or props because it was created before a re-render. This is the root cause of most useEffect bugs. Fix: include all referenced values in the dependency array, or use a ref to hold the latest value.

Prototypal inheritance and the event loop — understanding the call stack, microtask queue (Promises), and macrotask queue (setTimeout) explains why setState batching works and why certain async patterns behave unexpectedly.

Higher-order functions — map, filter, reduce are table stakes. More important: understanding how HOCs in React are just functions returning functions, and how custom hooks are closures over state.

Immutability — React's reconciler uses reference equality to detect changes. Mutating objects directly breaks change detection. Always return new references: {...obj, key: value}, [...arr, newItem].

Promises and async/await — understanding microtask scheduling matters when you're chaining async operations in useEffect or handling race conditions in data fetching.

WeakMap and WeakRef — relevant when building caching utilities or memoization outside React's built-ins, because they allow GC to collect entries when the key is no longer referenced.

Key interview point: Stale closures in useEffect are the most common senior-level trap. Always have a specific example ready.
Q2What are the different phases of the React component lifecycle and their use cases?▾

In the hooks model there are three conceptual phases:

Mount — component renders for the first time. useEffect(() => { ... }, []) runs after the first paint. Use for: initial data fetching, setting up subscriptions, DOM manipulation that needs the element to exist.

Update — re-renders triggered by state or prop changes. useEffect(() => { ... }, [dep]) runs when dep changes. Use for: syncing external systems with state, re-fetching when a filter changes, responding to prop changes.

Unmount — component is removed. The cleanup function returned from useEffect runs. Use for: clearing timeouts, unsubscribing from websockets, aborting fetch requests with AbortController, removing event listeners.

React 18 also introduced a concurrent rendering phase where React can pause, abort, and restart rendering. This is why effects should be idempotent — in Strict Mode, React intentionally mounts, unmounts, and remounts components to surface cleanup bugs.

useEffect(() => { const controller = new AbortController(); fetchData(id, controller.signal); return () => controller.abort(); // cleanup on unmount or dep change }, [id]);
Key interview point: Mention AbortController for cleanup — it shows you understand real-world side effect management, not just toy examples.
Q3What are the different approaches to state management in large-scale React applications?▾

Local state (useState / useReducer) — default choice. If only one component needs the data, keep it local. useReducer is better than useState when state transitions have logic — think a form with validation states, or a multi-step wizard.

Context API — for state shared across a subtree that doesn't update frequently. Good for: theme, auth user, locale. Bad for: high-frequency updates (every render of a Consumer re-renders all subscribers). Fix high-frequency Context with useMemo or by splitting contexts.

Zustand — lightweight, no boilerplate, subscription-based so components only re-render when their slice changes. Best default for global client state in 2024-25.

Redux Toolkit — best when you need predictable state machines, time-travel debugging, or complex action flows across many slices. The boilerplate complaint is mostly gone with RTK. Still overkill for most apps.

React Query / TanStack Query — for server state. Separating server state (what's in the DB) from client state (UI interactions) is the most important architectural decision in large apps. React Query handles caching, background refetch, stale-while-revalidate, optimistic updates — things Redux does badly.

URL state — often overlooked. Filters, pagination, selected tab — these belong in the URL so they survive refresh and are shareable. Use useSearchParams.

Key interview point: The insight interviewers want: "server state and client state are different problems and should be managed separately."
Q4What are the techniques to optimize re-rendering in React components?▾

React.memo — wraps a component so it only re-renders when its props change (shallow comparison). Effective when a parent re-renders often but the child's props are stable.

useMemo — memoizes a computed value. Use when the computation is expensive and its inputs don't change every render. Don't use for cheap computations — the memoization itself has overhead.

useCallback — memoizes a function reference. Important when passing callbacks to memoized children — without it, a new function reference is created every render, breaking memo.

State colocation — the most impactful optimization. If only a child needs a piece of state, don't put it in the parent. State at the right level means fewer unnecessary re-renders higher in the tree.

Context splitting — if a Context holds both frequently and rarely changing values, split them into two contexts. Subscribers to the stable one won't re-render when the fast-changing one updates.

List virtualization — react-window or TanStack Virtual. For lists of 100+ items, only render what's in the viewport. Critical for performance on large datasets.

Lazy loading — React.lazy + Suspense for route-level code splitting. Large libraries (charts, maps, editors) should only load when the user navigates to the page that needs them.

// Wrong: new function ref every render, breaks memo on Child <Child onClick={() => doSomething(id)} /> // Right: stable reference const handleClick = useCallback(() => doSomething(id), [id]); <Child onClick={handleClick} />
Q5What are the differences between controlled and uncontrolled components?▾

Controlled — React is the single source of truth for the input's value. The value is bound to state and every keystroke calls setState. You always know exactly what the input contains.

const [val, setVal] = useState(''); <input value={val} onChange={e => setVal(e.target.value)} />

Uncontrolled — the DOM owns the value. You use a ref to read it when needed (on submit). Less code, but you can't validate in real-time or conditionally disable submit.

const ref = useRef(); <input ref={ref} defaultValue="initial" /> // read with ref.current.value on submit

When to use which: Controlled for forms with real-time validation, conditional logic, or interdependent fields. Uncontrolled for simple forms where you only need the value on submit, or when integrating with non-React libraries that manage their own DOM.

React Hook Form uses uncontrolled inputs internally by default (with refs) for performance — it avoids re-rendering the whole form on every keystroke — while still giving you a controlled API surface. This is the best of both worlds for large forms.

Key interview point: Mention RHF's hybrid approach — it signals production awareness beyond the basic distinction.
Q6What are the best practices for organizing and structuring React components in a large codebase?▾

Feature-based folder structure over type-based. Don't put all components in /components, all hooks in /hooks. Instead: /features/auth/, /features/dashboard/ — each feature owns its components, hooks, utils, and types. Shared primitives go in /ui/ or /components/.

Barrel exports with caution — index.ts re-exports make imports cleaner but can cause circular dependency issues and slow down bundlers if overused. Use them at feature boundaries, not inside features.

Separate concerns explicitly:

— Presentational components: pure render, no data fetching, all data via props
— Container/page components: fetch data, manage state, compose presentational components
— Custom hooks: all logic that's reusable across components

Colocation principle — keep tests, styles, and types next to the component they belong to. Button.tsx, Button.test.tsx, Button.module.css in the same folder.

Single responsibility — if a component is over ~150 lines, it's doing too much. Extract sub-components or hooks. This also makes testing dramatically easier.

Consistent naming — components are PascalCase, hooks are camelCase starting with use, utility functions are camelCase. File names match component names exactly.

Q7What are the different ways to handle side effects in React?▾

useEffect — the primary tool. Runs after render. For: data fetching, subscriptions, DOM side effects. Always return a cleanup function for anything that needs teardown.

useLayoutEffect — runs synchronously after DOM mutations but before the browser paints. Use only for DOM measurements (reading element dimensions) or mutations that need to happen before the user sees the render. Using it for data fetching blocks painting and degrades performance.

Event handlers — for side effects triggered by user interaction. Don't put user-triggered logic in useEffect watching a flag — put it directly in the onClick handler. This is cleaner and avoids unnecessary renders.

React Query / SWR — for data fetching side effects specifically. They handle caching, deduplication, background refresh, and error states that you'd otherwise build manually in useEffect. For any real app, prefer these over raw useEffect for fetch calls.

Zustand or Redux middleware — for side effects that need to happen in response to state changes across the app, like logging, analytics, or syncing to localStorage.

useRef for imperative side effects — when you need to call a method on a DOM element or a third-party library directly (like a map instance, a video player), useRef gives you the handle without triggering re-renders.

Key interview point: "I prefer to keep side effects in event handlers when they're user-triggered, and in useEffect only when they need to sync with external systems." This shows nuanced understanding.
Q8What are the advantages and limitations of Redux for state management?▾

Advantages:

— Predictable state: state only changes through dispatched actions, making the flow easy to trace
— Time-travel debugging with Redux DevTools: you can replay actions and inspect state at any point
— Good for complex state machines with many interacting slices
— Excellent for teams — the strict pattern makes code predictable across contributors
— RTK (Redux Toolkit) has eliminated most of the original boilerplate complaints

Limitations:

— Still more verbose than Zustand or Context for simple cases
— Not designed for server state — people often use Redux to cache API responses, which leads to complex normalization logic that React Query handles automatically
— Performance: all connected components re-render when any part of the store changes unless you use selectors precisely. useSelector with poorly scoped selectors is a common perf bug
— Overkill for most apps — a medium-size app rarely needs Redux's guarantees
— Learning curve is real for new developers

Modern verdict: Redux Toolkit for apps that genuinely need complex client state machines. React Query for server state. Zustand for everything in between. The combination of React Query + Zustand covers 90% of real apps better than Redux alone.

Q9What are the considerations for integrating ES6+ features into React projects?▾

Destructuring — essential in React. Props destructuring in function signature keeps components readable. Array destructuring is how useState is consumed.

Spread operator — used constantly for immutable state updates and passing props. But be careful with prop spreading (<Component {...props}/>) — it passes unknown attributes to DOM elements and generates React warnings.

Optional chaining (?.) and nullish coalescing (??) — reduce defensive null checks in JSX. user?.profile?.avatar ?? defaultAvatar is cleaner than nested ternaries.

Dynamic imports — the foundation of React.lazy code splitting. const Chart = lazy(() => import('./Chart')) only loads the Chart bundle when the component is actually rendered.

Generators and async iterators — relevant for streaming responses (reading chunks from a ReadableStream in a for-await-of loop) and for complex async workflows in custom hooks.

Proxy — used internally by Immer (which RTK uses) to enable "mutating" syntax for immutable updates. Knowing this helps debug confusing Immer behavior.

Logical assignment operators (??=, ||=, &&=) — useful for default initialization patterns in reducers and config objects.

Bundler consideration — Vite and Next.js handle transpilation automatically. You don't manually configure Babel for most modern setups. Just write modern JS and let the toolchain handle targets.

Q10What are the implications of improper state management on React performance?▾

State too high in the tree — the most common issue. If you put state in a top-level component when only a leaf component needs it, every intermediate component re-renders on every state change, even though they don't use it. Fix: colocate state as low as possible.

Object/array references in state — creating new objects or arrays during render (e.g., style={{ color: 'red' }} inline) generates a new reference every render. Children receiving that as a prop will always re-render, breaking React.memo. Fix: useMemo or define outside the component.

Storing derived state — saving to state something that can be computed from existing state causes double renders and sync bugs. Derive it in the render or useMemo instead.

Context with high-frequency updates — every Context value change re-renders every consumer, even if the consumer only uses a part of the value that didn't change. This is why putting WebSocket messages or mouse coordinates in Context is a performance disaster.

Missing cleanup in useEffect — stale subscriptions, unresolved promises, and leaked event listeners accumulate over time and cause memory leaks and state updates on unmounted components (the "Can't perform a React state update on an unmounted component" error).

Cascading setState calls — calling setState multiple times in sequence outside of React's batching (pre-React 18) triggered multiple re-renders. React 18 auto-batches all state updates including async ones, but understanding this matters for legacy codebases.

Key interview point: "The most impactful thing I do for performance isn't memo or useMemo — it's making sure state lives at the right level in the tree."

Q1What are the key differences between Django and FastAPI, and when would you choose each?▾

Django — batteries-included framework. ORM, admin panel, auth, migrations, forms — all built in. Synchronous by default (WSGI), though Django 3.1+ supports async views. Best for: content-heavy apps, admin dashboards, teams that want conventions enforced, projects where rapid CRUD development matters more than raw throughput.

FastAPI — async-first, minimal, built on Starlette and Pydantic. No ORM or admin out of the box — you bring your own (SQLAlchemy, Tortoise ORM). Best for: high-throughput APIs, microservices, ML model serving, any service where async I/O performance matters.

Performance: FastAPI handles concurrent I/O-bound requests significantly better than sync Django because it doesn't block the event loop waiting for DB or network calls. Uvicorn/Gunicorn with async workers vs Django's threaded WSGI server.

Type safety: FastAPI uses Pydantic for automatic request validation and response serialization with type hints. Django REST Framework does this with serializers — more verbose but more flexible for complex nested writes.

Rule of thumb: Django if you need the full web framework. FastAPI if you're building a pure API service that needs async throughput.
Q2How does FastAPI's dependency injection system work, and what are its advantages?▾

FastAPI's DI system uses Depends() — you declare what a route needs as function parameters, and FastAPI resolves and injects them automatically.

async def get_db(): db = SessionLocal() try: yield db finally: db.close() @router.get("/users/{id}") async def get_user(id: int, db: Session = Depends(get_db)): return db.query(User).get(id)

Advantages:

— Composability: dependencies can depend on other dependencies. An auth dependency can depend on get_db. FastAPI resolves the tree.
— Testability: override dependencies in tests with app.dependency_overrides[get_db] = mock_db — no monkey-patching needed.
— Separation of concerns: route handlers stay clean, cross-cutting concerns (auth, rate limiting, DB sessions) live in reusable dependency functions.
— Lifecycle management: generator dependencies (using yield) automatically handle setup and teardown — DB sessions close, connections release.

Scopes: By default dependencies are re-evaluated per request. Use Depends(func, use_cache=True) (default) so the same dependency is only called once per request even if multiple routes depend on it.

Q3How does Pydantic v2 work and what are the important differences from v1?▾

Pydantic v2 (released 2023) rewrote the core in Rust, giving 5-50x faster validation. The API changed significantly.

Key v2 changes:

— @validator replaced by @field_validator (field-level) and @model_validator (cross-field)
— .dict() replaced by .model_dump(), .json() by .model_dump_json()
— orm_mode = True replaced by model_config = ConfigDict(from_attributes=True)
— __fields__ replaced by model_fields

from pydantic import BaseModel, field_validator, model_validator, ConfigDict class OrderCreate(BaseModel): model_config = ConfigDict(from_attributes=True) start_date: date end_date: date amount: float @field_validator('amount') @classmethod def amount_positive(cls, v): if v <= 0: raise ValueError('Amount must be positive') return v @model_validator(mode='after') def dates_valid(self): if self.end_date <= self.start_date: raise ValueError('end_date must be after start_date') return self

Q4How do you handle authentication and authorization properly in FastAPI?▾

Authentication — verifying identity. Standard approach: JWT with OAuth2PasswordBearer.

oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/auth/token") async def get_current_user(token: str = Depends(oauth2_scheme), db = Depends(get_db)): payload = decode_jwt(token) # raises 401 on invalid user = db.query(User).get(payload["sub"]) if not user: raise HTTPException(status_code=401) return user

Authorization — verifying permissions. Layer on top of auth with role checks:

def require_role(role: str): async def checker(user: User = Depends(get_current_user)): if user.role != role: raise HTTPException(status_code=403) return user return checker @router.delete("/admin/user/{id}", dependencies=[Depends(require_role("admin"))])

Refresh tokens — short-lived access tokens (15min) + long-lived refresh tokens (7 days) stored in httpOnly cookies. Rotate refresh tokens on each use.

Security considerations: Never store passwords in plain text — use bcrypt (passlib). Rate-limit the /token endpoint. Validate token audience and issuer claims. Use HTTPS only — JWT in Authorization header is meaningless over HTTP.

Q5What are Python's async/await mechanics and how does FastAPI use them?▾

Python's asyncio is a single-threaded event loop. When an await is hit, control returns to the event loop which can run other coroutines. No actual parallelism — concurrency through cooperative multitasking.

FastAPI on top of this: FastAPI runs on Uvicorn (ASGI server). For async route handlers, requests run on the event loop — thousands of concurrent I/O-bound requests with no thread overhead. For sync route handlers, FastAPI automatically runs them in a threadpool to avoid blocking the loop.

# Async: runs on event loop, can handle many concurrent requests @router.get("/data") async def get_data(db = Depends(get_async_db)): result = await db.execute(select(User)) # yields control while waiting return result.scalars().all() # Sync: FastAPI runs this in a threadpool automatically @router.get("/heavy") def heavy_compute(): return do_cpu_work() # doesn't block event loop

Common pitfall: Using a sync DB driver (like psycopg2) inside an async route handler blocks the event loop. Always use async drivers — asyncpg, aiosqlite, SQLAlchemy async — in async routes.

Q7How does Python handle memory management and what pitfalls exist in long-running services?▾

Python uses reference counting as the primary GC mechanism — objects are freed when their reference count drops to zero. A cyclic garbage collector handles reference cycles. CPython's GIL prevents true parallel execution of Python bytecode across threads.

Memory pitfalls in long-running services:

— Growing caches without bounds: an in-memory dict used as a cache that never evicts entries will grow forever. Use functools.lru_cache with maxsize, or a TTL-based cache like cachetools.
— Unclosed DB connections: SQLAlchemy sessions or raw connections that aren't closed return to the pool (or don't). Over time this exhausts the pool. Always use context managers or yield-based dependencies.
— Large objects in module scope: ML models, large config objects loaded at import time persist for the process lifetime. Fine intentionally, a leak if accidental.
— Celery worker memory growth: workers that process large documents accumulate memory. Set max_tasks_per_child to recycle workers periodically.
— Async task leaks: asyncio.create_task() without keeping a reference lets tasks get GC'd silently if they're not awaited. Always store task references.

Q8What are the best practices for error handling and logging in a FastAPI service?▾

Custom exception handlers: define domain exceptions and register global handlers so every route doesn't repeat try/except logic.

class NotFoundError(Exception): def __init__(self, resource: str): self.resource = resource @app.exception_handler(NotFoundError) async def not_found_handler(request, exc): return JSONResponse(status_code=404, content={"error": f"{exc.resource} not found"})

Structured logging: use structlog or Python's logging with a JSON formatter. Log request ID, user ID, endpoint, duration for every request. A middleware that injects a correlation ID into each request context makes distributed tracing feasible.

Never expose internals: catch all unhandled exceptions at the middleware level and return a generic 500. Stack traces go to logs, not to API responses.

HTTP status codes precisely: 400 for bad input, 401 for unauthenticated, 403 for unauthorized, 404 for not found, 422 for validation errors (FastAPI does this automatically for Pydantic errors), 409 for conflicts, 429 for rate limit, 500 for unexpected errors.

Key point: FastAPI automatically returns 422 with field-level details when Pydantic validation fails — don't duplicate this with manual try/except around validation logic.

Q10What are Python decorators and how are they used in FastAPI and Django?▾

A decorator is a function that takes a function and returns a modified function. Syntactic sugar for func = decorator(func).

def log_time(func): @wraps(func) # preserves __name__, __doc__ async def wrapper(*args, **kwargs): start = time.time() result = await func(*args, **kwargs) print(f"{func.__name__} took {time.time() - start:.2f}s") return result return wrapper @log_time async def process_document(doc_id: int): ...

In FastAPI: @router.get(), @router.post() are decorators that register routes. @app.middleware() decorates a middleware function. @field_validator and @model_validator in Pydantic models.

In Django: @login_required, @permission_required, @cache_page, @csrf_exempt — all view decorators. DRF uses @api_view to convert a function into an APIView.

Pitfall: Always use functools.wraps(func) inside a decorator — without it, the decorated function loses its original __name__ and __doc__, which breaks debugging and OpenAPI docs generation in FastAPI.

Q1What is the Python GIL and what are its implications for concurrent programming?▾

The Global Interpreter Lock is a mutex that allows only one thread to execute Python bytecode at a time within a single CPython process. It exists because CPython's memory management (reference counting) is not thread-safe — the GIL prevents race conditions on reference counts.

Implications:

— Threading for CPU-bound work is mostly useless — two threads don't actually run Python in parallel. You get context switching overhead without the parallelism benefit.
— Threading is fine for I/O-bound work — when a thread blocks on I/O (network, disk), it releases the GIL, letting other threads run. This is why Django's threaded WSGI works adequately.
— Multiprocessing bypasses the GIL — each process has its own interpreter and GIL. True parallel CPU execution.
— Async is GIL-unaffected — asyncio is single-threaded cooperative multitasking. Never holds the GIL waiting on I/O because it yields control instead.

Python 3.13 (PEP 703): experimental no-GIL build available. Not production-ready yet but signals direction.

Key interview point: "For a FastAPI service, the GIL is largely irrelevant — async I/O handles concurrency without threads. The GIL matters when I need CPU parallelism, which I push to Celery workers with multiprocessing."
Q2What is the event loop in Python asyncio, and how does it schedule tasks?▾

The event loop is a single-threaded scheduler that manages a queue of coroutines and I/O callbacks. It runs continuously, picking up tasks that are ready to execute.

Execution flow:

1. A coroutine is scheduled with asyncio.create_task() or await
2. It runs until it hits an await on an I/O operation
3. The loop registers the I/O with the OS (via epoll/kqueue/IOCP)
4. The loop picks up another ready coroutine
5. When the OS signals the I/O is done, the original coroutine is resumed

async def fetch_all(urls): async with aiohttp.ClientSession() as session: tasks = [fetch(session, url) for url in urls] return await asyncio.gather(*tasks) # all requests run concurrently

asyncio.gather vs asyncio.wait: gather runs all and returns results in order, raises on first exception by default. wait gives more control — you can handle first-completed or handle exceptions individually.

Blocking the event loop: Any synchronous code that runs for more than a few milliseconds — a slow DB query with a sync driver, a CPU computation, time.sleep() — blocks ALL other coroutines. Use asyncio.run_in_executor() to push blocking work to a threadpool.

Q3What are common caching strategies and how do you implement them in a Python API service?▾

Cache-aside (lazy loading) — app checks cache first; on miss, fetches from DB, writes to cache, returns. Most common pattern. Cache can become stale — handle with TTL.

async def get_user(user_id: int, redis: Redis, db): cached = await redis.get(f"user:{user_id}") if cached: return json.loads(cached) user = await db.get(User, user_id) await redis.setex(f"user:{user_id}", 300, user.model_dump_json()) # 5min TTL return user

Write-through — write to cache and DB simultaneously on every write. Cache is always fresh but every write has dual overhead. Good for read-heavy data that updates predictably.

Write-behind (write-back) — write to cache immediately, persist to DB asynchronously. Lower write latency, risk of data loss on crash. Used in high-write scenarios like counters.

Cache invalidation strategies: TTL-based (simplest), event-driven (publish invalidation events on writes), versioned keys (append version number to key, bump on write).

functools.lru_cache — in-process memoization for pure functions. Good for expensive computations with repeated inputs. Not distributed — each process has its own cache.

Key point: Cache invalidation is the second hardest problem in CS. Always ask: what's the acceptable staleness? That determines TTL and strategy.
Q4What is connection pooling and why does it matter for database performance?▾

Opening a new DB connection is expensive — TCP handshake, auth, session setup — typically 50-100ms. A connection pool maintains a set of pre-opened connections and reuses them across requests.

SQLAlchemy pool settings:

engine = create_async_engine( DATABASE_URL, pool_size=10, # permanent connections in pool max_overflow=20, # extra connections allowed under load pool_timeout=30, # wait time before "pool exhausted" error pool_recycle=1800, # recycle connections older than 30min (avoids stale connection errors) )

Pool exhaustion — when all connections are in use and a new request needs one, it waits up to pool_timeout. Under sustained high load, this causes latency spikes. Signals the pool is sized too small or queries are holding connections too long (long transactions).

PgBouncer — a connection pooler that sits in front of PostgreSQL. Allows thousands of app connections to be multiplexed onto a small number of real DB connections. Critical for high-concurrency apps — PostgreSQL performs poorly with hundreds of direct connections.

Connection leak — a connection checked out from the pool but never returned (due to missing finally/context manager) reduces effective pool size over time. SQLAlchemy's context managers prevent this when used correctly.

Q5What are race conditions in concurrent systems and how do you prevent them?▾

A race condition is when two operations read-then-write shared state and the final result depends on which runs first. Classic example: two requests both read a wallet balance of $100, both deduct $50, both write $50 — final balance should be $50 but becomes $50 instead of $0 because neither saw the other's write.

Prevention strategies:

Database-level locking:

# Pessimistic lock: SELECT FOR UPDATE blocks other reads until transaction completes async with db.begin(): wallet = await db.execute( select(Wallet).where(Wallet.id == id).with_for_update() ) wallet.balance -= amount # Optimistic lock: check version hasn't changed before committing UPDATE wallets SET balance = balance - :amount, version = version + 1 WHERE id = :id AND version = :expected_version

Redis atomic operations: INCR, DECR, SETNX are atomic — no race conditions possible. For complex operations, Lua scripts execute atomically on the server.

Database atomic updates: UPDATE ... SET count = count + 1 is atomic at the DB level — safer than read-modify-write in application code.

Idempotency keys: for financial operations, clients send a unique key per operation. Server stores processed keys — duplicate requests with the same key return the cached result without reprocessing.

Q6What is backpressure in async systems and how do you handle it?▾

Backpressure is when a consumer can't process data as fast as a producer sends it. Without handling, the queue grows unbounded and eventually crashes the system with memory exhaustion or timeouts.

In a task queue (Celery): if workers are slow, the Redis/RabbitMQ queue grows. Fix: set task_acks_late=True so tasks aren't acknowledged until processed, limit worker_prefetch_multiplier to prevent workers from grabbing tasks they can't process soon.

In async Python:

queue = asyncio.Queue(maxsize=100) # bounded queue async def producer(): await queue.put(item) # blocks when queue is full — natural backpressure async def consumer(): item = await queue.get() await process(item) queue.task_done()

At the API level: rate limiting is a form of backpressure — you push the load back to the client rather than absorbing it. Return 429 with a Retry-After header so clients know when to retry.

Circuit breaker pattern: if a downstream service starts failing, stop sending it requests for a period rather than piling up failed requests. Libraries like circuitbreaker implement this for Python.

Q7How do you profile and identify performance bottlenecks in a Python application?▾

For CPU profiling: cProfile (built-in) or py-spy (sampling profiler, attaches to a running process without code changes — critical for production profiling).

python -m cProfile -o output.prof your_script.py snakeviz output.prof # visual flame graph in browser

For async profiling: aiomonitor or pyinstrument which understands async call stacks. Standard cProfile misrepresents async code because await points show zero time.

For DB query profiling: SQLAlchemy echo mode logs all SQL with timing. In Django, Django Debug Toolbar or direct EXPLAIN ANALYZE. Look for N+1 queries — the query count scales with row count instead of being constant.

For memory profiling: tracemalloc (built-in, snapshots memory allocation by line), memory-profiler for line-by-line memory usage, objgraph to find reference cycles and leak sources.

In production: structured timing logs (log duration of each major operation), distributed tracing with OpenTelemetry + Jaeger, APM tools like Sentry Performance or Datadog. Never fly blind in production.

Q8What is the difference between horizontal and vertical scaling, and what limits each?▾

Vertical scaling — bigger machine (more CPU, RAM). Simple — no code changes. Limited by the largest available instance size and single point of failure. Effective until you hit the ceiling.

Horizontal scaling — more instances running in parallel behind a load balancer. No theoretical ceiling. Requires the application to be stateless — no in-memory session state, no local cache that differs per instance, no assumption about which instance handles a given request.

What breaks with horizontal scaling:

— In-memory caching: each instance has its own cache — move to Redis
— WebSocket sessions: a user's socket might connect to instance A but a message targeting them arrives at instance B — use Redis Pub/Sub adapter
— File uploads: a file written to local disk on instance A isn't visible to instance B — use S3 or equivalent
— Scheduled jobs: multiple instances all running the same cron job — use a distributed lock (Redis SETNX) or a dedicated scheduler (Celery Beat)

Database scaling: read replicas for read-heavy workloads. Sharding for write-heavy workloads at extreme scale. Both are complex — exhaust vertical and read replicas before going there.

Q9What are the patterns for handling distributed transactions and data consistency?▾

Distributed transactions — operations that span multiple services or databases — are one of the hardest problems in distributed systems. You can't use a single DB transaction across services.

Saga pattern: break the transaction into a sequence of local transactions. Each step publishes an event. If a step fails, compensating transactions undo previous steps.

Example: Order service creates order → Payment service charges card → Inventory service reserves stock. If inventory fails, publish compensate events to refund and cancel.

Outbox pattern: instead of publishing an event directly after a DB write (which can fail independently), write the event to an outbox table in the same DB transaction. A separate process polls the outbox and publishes. Guarantees at-least-once delivery.

BEGIN; INSERT INTO orders (id, status) VALUES (:id, 'pending'); INSERT INTO outbox (event_type, payload) VALUES ('order.created', :payload); COMMIT; -- Separate process: SELECT * FROM outbox WHERE published = false

Eventual consistency: accept that data across services won't be immediately consistent. Design UIs and business logic to handle temporary inconsistency. Use idempotency so retries don't cause duplicate operations.

Key point: At CoinEarth's scale (fintech), the outbox pattern and idempotency keys are essential — a double charge is a severe user experience failure.
Q10What is Celery and how do you design reliable task queues with it?▾

Celery is a distributed task queue. Tasks are Python functions decorated with @celery.task — when called with .delay() or .apply_async(), they're serialized and placed in a broker (Redis or RabbitMQ). Worker processes consume and execute them.

@celery.task( bind=True, max_retries=3, default_retry_delay=60, acks_late=True, # acknowledge only after successful execution reject_on_worker_lost=True # requeue if worker crashes mid-task ) def process_document(self, doc_id: int): try: result = run_ocr(doc_id) return result except TemporaryError as e: raise self.retry(exc=e, countdown=2 ** self.request.retries) # exponential backoff

Reliability considerations:

— acks_late=True — task stays in queue until acknowledged after processing. If worker crashes, task is requeued.
— Idempotency — tasks must be safe to run twice. A retry should produce the same result as the first run.
— Dead letter queue — tasks that exhaust retries go to a DLQ for manual inspection, not silently dropped.
— Task routing — route heavy tasks to dedicated workers so they don't starve quick tasks.
— Monitoring — Flower (Celery's web UI) or Prometheus metrics for queue depth, task failure rates, worker throughput.

Q1What are indexes, how do they work internally, and when should you add them?▾

An index is a separate data structure (typically a B-tree) that stores a sorted copy of one or more columns with pointers to the actual rows. Instead of scanning every row (seq scan), the DB traverses the tree — O(log n) instead of O(n).

B-tree index: default in PostgreSQL and MySQL. Supports equality and range queries (<, >, BETWEEN, LIKE 'prefix%'). Not useful for LIKE '%suffix' — can't use the prefix to navigate the tree.

Hash index: O(1) lookup for equality only. Can't do range queries. Rarely needed — B-tree is fast enough for most equality cases.

When to add:

— Columns in WHERE clauses of slow queries
— Foreign key columns (joining on unindexed FKs does seq scans on the referenced table)
— Columns in ORDER BY and GROUP BY for large result sets
— Composite indexes for queries with multiple WHERE conditions — column order matters: put the most selective column first

When NOT to add:

— Every column by default — indexes slow down writes (INSERT/UPDATE/DELETE must update all affected indexes)
— Low-cardinality columns (boolean, status with 3 values) — the optimizer often prefers a seq scan anyway
— Small tables — seq scan is faster than index lookup + row fetch for small datasets

-- Composite index for a common query pattern CREATE INDEX idx_feedback_trainer_date ON feedback(trainer_id, created_at DESC); -- Partial index: only index rows matching a condition CREATE INDEX idx_active_users ON users(email) WHERE active = true;
Q2What does EXPLAIN ANALYZE output tell you, and how do you use it to fix slow queries?▾

EXPLAIN shows the query plan the optimizer chose. EXPLAIN ANALYZE actually executes it and shows real timing.

EXPLAIN ANALYZE SELECT * FROM feedback WHERE trainer_id = 5 AND created_at > NOW() - INTERVAL '30 days';

Key things to look for:

— Seq Scan on a large table — the optimizer couldn't use an index. Either no index exists, or the query is too broad to benefit. Check the WHERE clause and add a targeted index.
— Rows estimate vs actual — if estimated 10 rows but actual was 10,000, statistics are stale. Run ANALYZE to update.
— Nested Loop with large row counts — a nested loop join on a large inner table is O(n×m). Usually means a missing index on the join column.
— Hash Join — generally efficient for large equi-joins. Watch for spill to disk if hash table exceeds work_mem.
— High cost on a specific node — drill into that node. Cost is in arbitrary units but relative cost across nodes reveals the bottleneck.

explain.depesz.com — paste EXPLAIN ANALYZE output for a visual breakdown with color-coded slow nodes.

Q3What are transactions, ACID properties, and isolation levels?▾

ACID:

— Atomicity: all operations in a transaction succeed or all are rolled back. No partial commits.
— Consistency: transaction leaves the DB in a valid state. Constraints (FK, NOT NULL, UNIQUE) are enforced.
— Isolation: concurrent transactions don't see each other's intermediate state.
— Durability: committed data survives crashes. Written to disk/WAL before acknowledging.

Isolation levels (PostgreSQL):

— Read Committed (default): each query in a transaction sees data committed before that query started. Prevents dirty reads. Allows non-repeatable reads (same query twice returns different results if another transaction committed between them).
— Repeatable Read: all queries in a transaction see data as of the transaction start. Prevents non-repeatable reads. Allows phantom reads in SQL standard — PostgreSQL prevents these too.
— Serializable: transactions behave as if executed serially. Highest consistency, lowest concurrency. Use for financial operations where read-then-write correctness is critical.

BEGIN ISOLATION LEVEL REPEATABLE READ; SELECT balance FROM wallets WHERE id = 1; -- reads consistent snapshot UPDATE wallets SET balance = balance - 50 WHERE id = 1; COMMIT;
Q4What are window functions and when are they more appropriate than GROUP BY?▾

Window functions perform calculations across a set of rows related to the current row, without collapsing rows into groups like GROUP BY does. You keep all rows and add a computed column.

-- Rank trainers by rating within their skill category SELECT trainer_id, skill, avg_rating, RANK() OVER (PARTITION BY skill ORDER BY avg_rating DESC) as rank_in_category, AVG(avg_rating) OVER (PARTITION BY skill) as category_avg, LAG(avg_rating, 1) OVER (ORDER BY created_at) as previous_rating FROM trainer_performance; -- Running total of payments per user SELECT user_id, amount, created_at, SUM(amount) OVER (PARTITION BY user_id ORDER BY created_at) as running_total FROM payments;

Use GROUP BY when: you need one row per group (counts, sums, averages at the aggregate level).

Use window functions when: you need both the row-level detail and an aggregate. Getting the top N per group is the classic window function use case — RANK() or ROW_NUMBER() with PARTITION BY, then filter WHERE rank <= N in a CTE or subquery.

-- Top 3 trainers per skill category WITH ranked AS ( SELECT *, RANK() OVER (PARTITION BY skill ORDER BY avg_rating DESC) as rk FROM trainers ) SELECT * FROM ranked WHERE rk <= 3;
Q5What are CTEs and what are the performance implications of using them?▾

A Common Table Expression (WITH clause) defines a named subquery you can reference within the main query. It improves readability and avoids repeating complex subqueries.

WITH active_trainers AS ( SELECT id, name FROM trainers WHERE active = true AND verified = true ), recent_feedback AS ( SELECT trainer_id, AVG(rating) as avg_rating, COUNT(*) as count FROM feedback WHERE created_at > NOW() - INTERVAL '90 days' GROUP BY trainer_id ) SELECT t.name, f.avg_rating, f.count FROM active_trainers t JOIN recent_feedback f ON f.trainer_id = t.id WHERE f.count >= 5 ORDER BY f.avg_rating DESC;

Performance implications in PostgreSQL:

— Pre-PostgreSQL 12: CTEs were "optimization fences" — always materialized (executed once, results stored in memory). The planner couldn't push predicates into them.
— PostgreSQL 12+: CTEs are inlined by default (treated like subqueries, planner can optimize). Use WITH ... AS MATERIALIZED explicitly if you want the old behavior (when the CTE is referenced multiple times and you want it computed once).

Recursive CTEs — for hierarchical data (org charts, category trees, graph traversal):

WITH RECURSIVE org_tree AS ( SELECT id, name, manager_id, 0 as depth FROM employees WHERE manager_id IS NULL UNION ALL SELECT e.id, e.name, e.manager_id, ot.depth + 1 FROM employees e JOIN org_tree ot ON e.manager_id = ot.id ) SELECT * FROM org_tree ORDER BY depth, name;
Q6What is normalization vs denormalization, and how do you decide which to use?▾

Normalization — organizing data to reduce redundancy. Each fact stored once. Updates only in one place. Achieved through normal forms (1NF → 2NF → 3NF).

— Advantage: no update anomalies, smaller storage, integrity enforced by FK constraints
— Disadvantage: reads require JOINs — more complex queries, potentially slower for read-heavy workloads

Denormalization — intentionally adding redundancy to optimize reads. Storing a user's name in the orders table instead of joining back to users.

— Advantage: fewer JOINs, simpler queries, faster reads
— Disadvantage: update anomalies (change a username, must update every order row), larger storage

Decision framework:

— Start normalized. Denormalize only when you have a measured performance problem, not upfront.
— Analytical/reporting queries are the main use case for denormalization — pre-aggregate or store redundant fields for dashboards.
— JSONB columns in PostgreSQL are a middle ground — store semi-structured data without a rigid schema, while keeping relational structure for the core entities.
— Materialized views: query a normalized schema, pre-aggregate into a materialized view, refresh on schedule. Best of both worlds for reporting.

Q7What are the different types of JOINs and when does each produce different results?▾
-- INNER JOIN: only rows with matches on both sides SELECT u.name, o.amount FROM users u INNER JOIN orders o ON o.user_id = u.id; -- Users with no orders are excluded -- LEFT JOIN: all rows from left, NULL for right if no match SELECT u.name, o.amount FROM users u LEFT JOIN orders o ON o.user_id = u.id; -- Users with no orders appear with NULL amount -- RIGHT JOIN: all rows from right (rare, usually rewrite as LEFT JOIN) -- FULL OUTER JOIN: all rows from both, NULL for missing matches SELECT u.name, o.amount FROM users u FULL OUTER JOIN orders o ON o.user_id = u.id; -- CROSS JOIN: cartesian product (every row with every row) -- Rarely intentional — usually a mistake. Result = n × m rows. -- SELF JOIN: joining a table to itself (hierarchies, comparisons) SELECT e.name, m.name as manager FROM employees e LEFT JOIN employees m ON m.id = e.manager_id;

Common mistake: filtering on a LEFT JOIN's right-side column in WHERE effectively converts it to an INNER JOIN — NULL rows are excluded by the filter. Use the condition in the ON clause instead, or filter for IS NULL / IS NOT NULL explicitly.

Q8What is the N+1 query problem and how do you detect and fix it?▾

N+1 occurs when you fetch N parent records and then issue one query per record to fetch related data — 1 + N queries instead of 2.

# N+1: 1 query for trainers + 1 query per trainer for feedback trainers = db.query(Trainer).all() # 1 query for t in trainers: print(t.feedback) # triggers N queries (lazy loading) # Fixed with eager loading — 2 queries total trainers = db.query(Trainer).options(selectinload(Trainer.feedback)).all()

Detection: SQLAlchemy echo mode logs every query — count queries proportional to results. Django Debug Toolbar shows duplicate/similar queries. In production, slow query logs or APM tools surfacing queries that repeat with different IDs.

SQLAlchemy strategies:

— joinedload: single JOIN query — one round trip. Problem: duplicates parent rows for one-to-many, can be large
— selectinload: two queries — fetch parents, then fetch all related in one IN query. Usually the better choice for one-to-many
— subqueryload: similar to selectinload but uses a subquery — less common in modern SQLAlchemy

In raw SQL: a single JOIN fetches everything in one query. N+1 is an ORM-specific issue from lazy loading defaults.

Q9What are database constraints and why are they important beyond application-level validation?▾

Constraints are rules enforced at the database level, not just in application code. They're the last line of defense against bad data.

Types:

— NOT NULL: column must have a value. Prevents accidental nulls from bugs or missing defaults.
— UNIQUE: no duplicate values. Critical for email, username, idempotency keys. Creates an index automatically.
— PRIMARY KEY: NOT NULL + UNIQUE + clustered index.
— FOREIGN KEY: referential integrity — can't create an order for a non-existent user. Options: RESTRICT (default), CASCADE (delete orders when user deleted), SET NULL.
— CHECK: custom condition that every row must satisfy.

CREATE TABLE feedback ( id BIGSERIAL PRIMARY KEY, trainer_id BIGINT NOT NULL REFERENCES trainers(id) ON DELETE CASCADE, rating SMALLINT NOT NULL CHECK (rating BETWEEN 1 AND 5), created_at TIMESTAMPTZ NOT NULL DEFAULT NOW() );

Why not rely on application validation alone: multiple services writing to the same DB, data migrations bypassing app logic, bugs that bypass validation, direct DB access for maintenance. Constraints prevent corruption that application code can't catch.

Deferred constraints: PostgreSQL allows constraints to be deferred to commit time — useful for circular references or bulk imports where intermediate states would violate constraints.

Q10What is database partitioning, and when is it appropriate?▾

Partitioning splits a large table into smaller physical pieces (partitions) while presenting a single logical table. Queries that filter on the partition key only scan relevant partitions (partition pruning).

Partition strategies:

— Range partitioning: by date ranges. Most common for time-series data — feedback, logs, events. Old partitions can be dropped instantly (DROP TABLE is instant, DELETE on millions of rows is slow).

CREATE TABLE feedback ( id BIGINT, trainer_id BIGINT, rating SMALLINT, created_at DATE ) PARTITION BY RANGE (created_at); CREATE TABLE feedback_2025_q1 PARTITION OF feedback FOR VALUES FROM ('2025-01-01') TO ('2025-04-01'); CREATE TABLE feedback_2025_q2 PARTITION OF feedback FOR VALUES FROM ('2025-04-01') TO ('2025-07-01');

— Hash partitioning: by hash of a column (e.g., user_id). Distributes rows evenly. Good for sharding read/write load across disk volumes.
— List partitioning: by discrete values (country, region). Good for geographic data or multi-tenant schemas.

When to use: tables with 100M+ rows where you regularly query by a date range or specific key. Not for small-medium tables — the overhead adds complexity without benefit.

Gotcha: indexes are local to partitions by default. Global indexes across partitions exist but have overhead. Make sure the partition key is in your most common WHERE clauses.
